# 🚀 Express-Typescript-Template

**A clean, production-ready Express.js starter template written in TypeScript.**

[![TypeScript](https://img.shields.io/badge/TypeScript-5.6-blue)](#)
[![Express](https://img.shields.io/badge/Express-5.x-black)](#)
[![License](https://img.shields.io/badge/License-ISC-green)](#)

</div>

A reusable backend starter with environment config, request validation, centralized error handling, structured logging (file + MongoDB), request tracing, and API versioning already wired up — so every new project starts from a solid foundation instead of from scratch.

---

## ✨ Features

- ⚡ **Express 5** with **TypeScript** — full type safety across routes, middleware, and controllers
- 🔐 **Environment Config** — `dotenv`-based, with a documented `.env.example`
- ✅ **Request Validation** — schema-based validation with `zod`
- 🛡️ **Centralized Error Handling** — a single error-handling middleware, consistent error responses
- 📝 **Structured Logging** — `winston` with:
  - Daily rotating log files (`winston-daily-rotate-file`)
  - MongoDB transport for queryable logs (`winston-mongodb`)
- 🔍 **Request Tracing** — every request tagged with a `uuid` for traceability across logs
- 🔢 **API Versioning** — routes namespaced (e.g. `/api/v1/...`) so breaking changes don't break existing consumers
- 🎨 **Prettier** — consistent code formatting out of the box
- 🔄 **Hot Reload** — `nodemon` + `ts-node` for a fast dev loop

## 🚀 Quick Start

```bash
git clone https://github.com/Vineeth-28/Express-Typescript-Template.git
cd Express-Typescript-Template
npm install
cp .env.example .env   # then fill in your own values
npm run dev
```

Server starts on `http://localhost:3000` (or whatever `PORT` you set).

See [SETUP.md](./SETUP.md) for the full step-by-step guide, including MongoDB setup and troubleshooting.

## 📝 Logging

Logging is handled by **Winston** with two transports:

1. **Daily rotating file logs** (`winston-daily-rotate-file`) — written to `logs/`, rotated daily, so disk usage stays bounded over time.
2. **MongoDB transport** (`winston-mongodb`) — logs are also written to the database configured via `MONGODB_URI`, so they're queryable without SSH-ing into a server.

Every incoming request is tagged with a unique **UUID** (via the `uuid` package) at the start of the request lifecycle, and that ID flows through all log lines for that request — making it possible to trace a single request across multiple log entries.

---

## ✅ Request Validation

Validation is handled with **Zod**. Define a schema per route/payload shape, then validate in middleware before the request reaches your controller — invalid requests are rejected early with a consistent error shape, instead of every controller re-validating input by hand.

---

## 🛡️ Error Handling

A single centralized error-handling middleware sits at the end of the middleware chain. Route handlers and services throw or forward errors (via `next(err)`), and the error handler is responsible for:

- Logging the error (through Winston, with the request's UUID attached)
- Returning a consistent JSON error response
- Hiding internal error details from the client in production

---

## 🔢 API Versioning

Routes are namespaced by version (e.g. `/api/v1/...`), so future breaking changes can ship as `/api/v2/...` without breaking existing consumers of `v1`.
